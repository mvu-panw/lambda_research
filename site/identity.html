Identity Security

What Lambda runs for workforce identity, what it gives customers, and where PANW identity security fits. Researched November 6, 2026.

Bottom line: Lambda's workforce identity is a Google Workspace shop with an IdP that is almost certainly Okta (not confirmed by name). Joiner, mover, and leaver changes are HR-driven, but access reviews happen only once a year. A new Enterprise Security role (posted September 24, 2026) spells out the near-term roadmap: role-matched identity automation, secure access for contractors and personal devices, controls on where AI agents send company data, and sandboxes for agents running off laptops. That list maps almost one-to-one onto Prisma Access Browser, AI Access Security, CyberArk, and Cortex ITDR. On the customer side, Lambda Cloud API keys carry full access to every API operation, and Private Cloud VPN access is a password-based FortiClient login by default.

What Lambda gives its customers (product IAM)

Lambda Cloud (On-Demand, 1CC)

  • RBAC with user identities, service identities, and groups. Five account roles and two workspace roles: Account Admin, Account Member, IAM Admin, Billing Admin, Support Ticketing Admin, Workspace Owner, Workspace Member. Confirmed roles
  • Workspaces are the isolation boundary. Resources in one workspace cannot reach another. docs
  • SSO (SAML or OIDC) is available only to 1-Click Cluster customers, and only by invitation through the account manager. Users are provisioned just in time at first login, and domain ownership is proven with a DNS TXT record. No SCIM is documented. Confirmed SSO
  • API keys "have full access to all Lambda API operations." They are long-lived and unscoped, with no expiry or IP binding documented. Service-identity keys can be governed through role assignment. Confirmed docs
  • Audit events come from an API endpoint only, retained for 6 months. They cover identity bans and suspensions, role changes, API and SSH key creation, and workspace membership. No push or SIEM export is documented. docs
  • 1CC compute access goes through a management node used as a jump box, or through JupyterLab behind a public reverse tunnel with a per-node random token shown in the console. docs

Private Cloud / Superclusters

  • OS access: Lambda installs one customer-supplied SSH key with root on every node, and after handoff the customer manages local users. Confirmed posture
  • VPN: a FortiGate client VPN. Lambda shares admin VPN credentials at handoff, and customers "may … integrate with their own identity provider for SSO". The published setup guide turns SSO off and uses a username and password from 1Password. Confirmed access guide
  • Lambda operator access: in the Managed Private Cloud model, Lambda keeps logical access. The customer can revoke it and gets audit logs of Lambda's actions. The Physical only model removes Lambda's logical access entirely. posture
  • Managed Kubernetes includes OIDC or SAML SSO "out of the box", with no SSH to nodes. Service accounts get static token kubeconfigs from Lambda's helper script. MK8s
  • Managed Slurm users can be linked to their console (SSO) identity by workspace email. mSlurm
  • BMC: "secure BMC passwords" are set. The docs do not say how BMC credentials are rotated or brokered. posture

All product IAM facts come from docs.lambda.ai (in the local corpus). Search corpus/docs/ for iam, predefined-roles, enabling-sso, and security-posture.

Talk track

  1. "Your job post is our product sheet." Contractor and BYOD access, AI agent data controls, and agent sandboxes are Lambda's own words from September 2026. Lead with Prisma Access Browser and AI Access Security, then use them to expand into SASE.
  2. "Keep Okta. Add privilege." PANW doesn't need to rip out the IdP. CyberArk adds just-in-time privileged access and continuous reviews on top of it.
  3. "Your customers will ask who at Lambda can touch their cluster." Managed Private Cloud promises revocable, audited Lambda access. Brokered and recorded operator sessions turn that promise into evidence for hyperscale and DoD procurement.
  4. "One identity story, edge to SOC." GlobalProtect SAML at the customer edge, User-ID on the management firewall, and XSIAM ITDR for revocation, all on the same platform as the firewall recommendation.

Discovery questions

  1. Which IdP is the system of record, Okta or Entra? Is lambdal.okta.com (Classic) a legacy tenant being migrated to Identity Engine?
  2. Which HR and ticketing systems drive provisioning? Is SCIM used for SaaS, and how often do access reviews run?
  3. How do engineers get privileged access to AWS, GCP, Kubernetes, BMCs, and DPUs today: standing roles, a bastion, or a PAM tool?
  4. How do Lambda operators access a Managed Private Cloud, and what do the customer-facing audit logs come from?
  5. What is the plan for contractors and personal devices: VDI, enrollment, or a browser-based control?
  6. Which AI tools and agents do employees use, and is anything sanctioned versus blocked? Where do agents run, and what credentials do they hold?
  7. Which SIEM, SOAR, and EDR are in place, and are IdP logs in the SIEM with automated session revocation?
  8. Are scoped or expiring API keys and SCIM on the Lambda Cloud roadmap? Do enterprise buyers ask for them?
